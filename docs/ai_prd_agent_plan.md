# AI PRD/기획서 생성 챗봇 도입 플랜

## 0. 전제

이 문서에 들어 있는 질문, 기능 목록, 꼬리질문, 기술 스택, 아키텍처 항목은 모두 제품 설계를 설명하기 위한 예시다. 실제 서비스에서 사용자에게 보여줄 질문과 답변, 기능 추천, 문서 생성 결과는 OpenAI API를 통해 동적으로 생성한다.

고정된 설문지를 순서대로 보여주는 방식이 아니라, 사용자의 입력과 이전 답변을 OpenAI API가 해석한 뒤 다음 질문, 추천 기능, 누락 정보, PRD/기획서 내용을 생성하는 챗봇형 에이전트로 구현한다.

## 1. 목표

비개발자 의뢰자가 "이런 사이트를 만들고 싶어요" 수준의 자연어 설명만 입력해도, AI 챗봇이 필요한 질문을 이어가며 웹사이트 개발 의뢰에 필요한 기획서와 PRD 문서를 자동 생성하는 기능을 추가한다.

핵심 목표는 다음과 같다.

- 개발 지식이 없는 사용자도 쉽게 의뢰 내용을 정리할 수 있게 한다.
- 개발자가 견적, 일정, 기능 범위, 기술 판단을 하기 쉬운 형태의 문서를 만든다.
- 무료로 기본 PRD/기획서를 생성해 포트폴리오 사이트의 문의 전환율을 높인다.
- 사용자가 "예약 사이트", "쇼핑몰"처럼 짧게 입력해도 보편적인 기능을 제안하고 선택하게 하여 요구사항을 완성한다.
- 유료 전문가 모드에서는 동시성, 결제 안정성, 데이터 모델, 운영 아키텍처, 기술 스택까지 구체화한다.
- 실제 PG 계약 전에는 결제 시뮬레이션으로 전문가 모드 구매 의사를 검증한다.
- 최종 산출물은 복사, 다운로드, 문의 전송까지 자연스럽게 이어지게 한다.

## 2. 대상 사용자

### 2.1 1차 사용자

- 쇼핑몰, 예약 사이트, 회사 홈페이지, 랜딩페이지, 커뮤니티, SaaS 도구 등을 만들고 싶은 비개발자
- 개발 의뢰를 처음 해보는 소상공인, 스타트업 창업자, 개인 브랜드 운영자
- 아이디어는 있지만 기능 정의, 화면 구성, 개발 범위를 문서화하기 어려운 사용자

### 2.2 2차 사용자

- 의뢰 내용을 검토하고 견적을 산정해야 하는 개발자
- 사용자의 요구사항을 바탕으로 상담을 진행해야 하는 프로젝트 담당자

## 3. 핵심 사용자 시나리오

1. 사용자가 포트폴리오 사이트에서 "AI 기획서 만들기" 버튼을 누른다.
2. 챗봇이 어떤 사이트를 만들고 싶은지 자연어로 묻는다.
3. 사용자가 "펜션 예약 사이트를 만들고 싶어요"처럼 간단히 답한다.
4. AI가 업종, 대상 고객, 필수 기능, 참고 사이트, 예산, 일정, 관리자 기능 등을 단계적으로 질문한다.
5. AI가 해당 사이트 유형에 보편적으로 필요한 기능을 제안하고, 사용자가 필요한 항목만 선택하게 한다.
6. 사용자가 모르는 항목은 "잘 모르겠어요"라고 답해도 AI가 추천안을 제시한다.
7. 충분한 정보가 모이면 AI가 다음 문서를 생성한다.
8. 사용자는 생성된 문서를 복사하거나 Markdown/PDF로 다운로드한다.
9. 원하면 문서를 문의 폼에 첨부해 개발 상담을 요청한다.
10. 더 깊은 기술 검토가 필요하면 유료 전문가 모드로 전환해 아키텍처와 구현 전략 문서를 생성한다.
11. 전문가 모드 가격을 확인한 사용자는 결제하기 버튼을 누르고, 실제 PG 연동 전까지는 자체 결제 시뮬레이션을 통해 결제 의사를 검증한다.
12. 결제 완료 화면에서는 베타 테스트 단계이며 실제 결제가 발생하지 않았음을 안내하고 상담 신청, 대기자 등록, 쿠폰 발급으로 이어지게 한다.

## 5. 챗봇 대화 설계

챗봇은 한 번에 많은 양식을 보여주지 않고, 사용자의 답변 수준에 맞춰 질문을 나눈다.

### 5.1 시작 질문

예시이며, 실제 문구는 OpenAI API가 대화 맥락에 맞춰 생성한다.

```text
어떤 사이트나 서비스를 만들고 싶으신가요?
짧게 적어주셔도 괜찮아요. 예: 병원 홈페이지, 예약 사이트, 쇼핑몰, 커뮤니티, 사내 관리 도구
```

### 5.2 필수 수집 항목

아래 항목은 PRD 품질을 위해 수집하면 좋은 정보의 예시다. 실제 질문 순서와 질문 문구는 OpenAI API가 대화 맥락에 맞춰 결정한다.

- 프로젝트 이름 또는 임시 이름
- 만들고 싶은 사이트 유형
- 사업/서비스 설명
- 주요 사용자
- 사용자가 사이트에서 해야 하는 행동
- 관리자에게 필요한 기능
- 필수 페이지
- 필수 기능
- 참고 사이트
- 디자인 선호도
- 예산 범위
- 희망 일정
- 출시 우선순위
- 결제, 예약, 로그인, 알림, 지도, 파일 업로드 등 특수 기능 여부

### 5.3 질문 방식

사용자에게 부담을 줄이기 위해 질문은 1개씩 던지는 것을 기본으로 한다. 단, 선택지가 명확한 경우에는 버튼형 선택지를 제공한다.

아래 선택지는 UI와 응답 구조를 설계하기 위한 예시이며, 실제 선택지 구성은 OpenAI API 응답을 기반으로 한다.

- 사이트 종류: 회사 홈페이지 / 쇼핑몰 / 예약 사이트 / 랜딩페이지 / 커뮤니티 / 관리자 도구
- 로그인 필요 여부: 필요 / 불필요 / 아직 모름
- 결제 필요 여부: 필요 / 불필요 / 나중에 추가
- 문서 상세도: 간단 버전 / 표준 버전 / 상세 버전

### 5.4 "잘 모르겠어요" 처리

비개발자가 막히는 지점을 줄이기 위해 모든 질문에는 기본 추천안을 제공한다.

예시이며, 실제 추천안은 OpenAI API가 프로젝트 맥락에 맞춰 생성한다.

```text
잘 모르셔도 괜찮아요. 펜션 예약 사이트라면 보통 객실 목록, 예약 달력, 예약 신청, 관리자 예약 확인, 문자/이메일 알림 기능이 필요합니다. 이 방향으로 초안을 잡아드릴까요?
```

### 5.5 짧은 입력 기반 기능 추천

사용자가 "예약 사이트", "쇼핑몰", "커뮤니티"처럼 짧게 입력해도 에이전트는 즉시 사이트 유형을 분류하고 보편 기능을 제안한다. 이 단계의 목적은 사용자가 직접 기능명을 몰라도 필요한 기능을 고를 수 있게 만드는 것이다.

동작 방식:

1. 사용자의 첫 입력에서 사이트 유형을 추론한다.
2. 해당 유형의 기본 기능 목록을 제안한다.
3. 각 기능을 "필수", "있으면 좋음", "나중에"로 분류하게 한다.
4. 선택된 기능을 바탕으로 추가 꼬리질문을 생성한다.
5. 사용자가 선택하지 않은 기능은 제외 범위에 기록한다.

예시이며, 실제 기능 추천과 문구는 OpenAI API가 생성한다.

```text
예약 사이트라면 보통 아래 기능들이 많이 들어갑니다.

필요한 기능을 골라주세요.
- 상품/객실/서비스 목록
- 예약 가능 날짜와 시간 표시
- 예약 신청 또는 즉시 예약
- 예약 확정/취소 관리
- 관리자 예약 현황 확인
- 문자/이메일/카카오 알림
- 결제 연동
- 쿠폰 또는 할인
- 후기 관리

이 중에서 꼭 필요한 기능이 있을까요?
잘 모르겠다면 기본 추천 구성으로 잡아드릴게요.
```

### 5.6 사이트 유형별 기본 추천 기능 예시

아래 목록은 OpenAI API 프롬프트와 UI 설계를 위한 예시다. 실제 서비스에서는 이 목록을 그대로 하드코딩해서 질문하지 않고, 사용자의 업종, 규모, 예산, 일정, 답변 맥락에 따라 OpenAI API가 필요한 기능과 꼬리질문을 생성한다.

#### 예약 사이트 예시

- 서비스/상품/객실 목록
- 상세 페이지
- 예약 가능 날짜와 시간
- 예약 신청 폼
- 예약 확정/취소
- 관리자 예약 캘린더
- 예약자 정보 관리
- 알림 발송
- 결제 연동
- 노쇼 및 환불 정책

꼬리질문 예시:

- 같은 시간에 여러 명이 예약할 수 있나요, 한 명만 예약할 수 있나요?
- 예약은 바로 확정되나요, 관리자가 승인해야 확정되나요?
- 결제까지 받아야 하나요, 예약 신청만 받으면 되나요?
- 예약 변경과 취소는 사용자가 직접 할 수 있어야 하나요?
- 관리자에게 달력 형태의 예약 현황이 필요할까요?

#### 쇼핑몰 예시

- 상품 목록
- 상품 상세
- 장바구니
- 주문/결제
- 배송지 입력
- 주문 내역
- 관리자 상품 관리
- 재고 관리
- 쿠폰/할인
- 리뷰/문의
- 교환/환불 관리

꼬리질문 예시:

- 판매 상품 수는 대략 몇 개인가요?
- 재고가 품절되면 자동으로 구매를 막아야 하나요?
- 옵션이 필요한가요? 예: 색상, 사이즈, 수량
- 결제 수단은 카드, 계좌이체, 간편결제 중 무엇이 필요할까요?
- 배송 추적이나 송장 번호 입력 기능이 필요할까요?

#### 회사/브랜드 홈페이지 예시

- 메인 페이지
- 회사 소개
- 서비스 소개
- 포트폴리오/사례
- 공지사항 또는 블로그
- 문의 폼
- 지도/오시는 길

꼬리질문 예시:

- 문의는 전화, 이메일, 카카오톡, 폼 중 어떤 방식이 좋을까요?
- 직접 수정해야 하는 콘텐츠가 있나요?
- 포트폴리오나 고객 사례를 몇 개 정도 보여줄까요?

#### 커뮤니티 예시

- 회원가입/로그인
- 게시판
- 댓글
- 좋아요/북마크

- 익명 글쓰기가 필요한가요?
- 사용자가 늘어났을 때 운영자가 관리할 기준이 있나요?

#### 관리자 도구/SaaS 예시

- 대시보드
- 로그인 및 권한
- 데이터 목록/검색/필터

- 어떤 데이터를 가장 자주 검색하거나 수정하나요?
- 엑셀 업로드나 다운로드가 필요한가요?
- 변경 이력을 남겨야 하나요?

### 5.7 기능 추가 유도 원칙

에이전트는 사용자가 더 큰 범위를 무조건 선택하도록 압박하지 않는다. 대신 개발 비용, 운영 편의성, MVP 우선순위를 함께 설명해 합리적으로 선택하게 한다.

권장 문장 예시:

```text
이 기능은 예약 누락을 줄이는 데 도움이 됩니다. 다만 처음 버전에서는 관리자 확인 방식으로 단순하게 시작하고, 사용자가 늘어난 뒤 자동 확정 기능을 추가하는 것도 괜찮습니다.
```

기능 추천은 다음 기준으로 표시한다.

- `필수`: 해당 유형에서 거의 항상 필요한 기능
- `추천`: 있으면 전환율이나 운영 효율이 좋아지는 기능
- `선택`: 예산과 일정에 따라 나중에 추가해도 되는 기능
- `주의`: 구현 난이도나 운영 리스크가 있어 별도 확인이 필요한 기능

## 6. 생성 산출물

### 6.1 PRD 문서

PRD는 개발자가 바로 기능 범위와 우선순위를 파악할 수 있게 구성한다.

포함 항목:

- 프로젝트 개요

- 대상 사용자

- 기능 요구사항
- 비기능 요구사항
- 페이지 목록
- 관리자 기능
- 외부 연동
- 데이터 항목
- 우선순위
- MVP 범위
- 제외 범위
- 일정 가정
- 리스크 및 확인 필요 사항

## 7. 화면 구성안

### 7.1 진입 버튼

포트폴리오 사이트의 문의 섹션 또는 프로젝트 섹션 근처에 다음 CTA를 추가한다.

- "AI로 기획서 만들기"
- "개발 의뢰서 자동 작성"
- "PRD 무료 생성하기"

### 7.2 챗봇 화면

권장 구성:

- 좌측 또는 중앙: 대화 영역
- 하단: 입력창
- 우측 또는 하단 탭: 생성 문서 미리보기
- 상단: 진행률 표시
- 완료 후: 복사, 다운로드, 문의하기 버튼

### 7.3 문서 미리보기

생성 중에는 섹션별로 문서가 채워지는 느낌을 준다.

탭 구성:

- 요약
- PRD
- 상세 기획서
- 확인 질문
- 전문가 모드

### 7.4 전문가 모드 업셀 화면

무료 문서 생성이 끝난 뒤 다음 조건에 해당하면 전문가 모드를 자연스럽게 제안한다.

- 예약, 결제, 재고, 좌석, 쿠폰처럼 동시에 여러 사용자가 같은 자원에 접근하는 기능이 있다.
- 관리자 권한, 정산, 알림, 외부 API 연동이 많다.
- 사용자가 "트래픽이 많을 것 같다", "안정성이 중요하다", "장기적으로 서비스화하고 싶다"고 답했다.
- 개발자에게 바로 전달할 기술 설계서가 필요하다.

예시 문구:

```text
이 프로젝트는 예약 중복 방지와 결제 처리 안정성이 중요해 보입니다.
전문가 모드에서는 동시성 처리 방식, DB 구조, API 설계, 추천 기술 스택까지 정리한 개발자용 설계서를 추가로 만들 수 있습니다.
```

### 7.5 결제 의사 검증 플로우

전문가 모드는 초기 MVP에서 실제 PG 계약 없이 결제 의사를 검증한다. PG사 테스트모드를 쓰지 않고, 사이트 내부에서 결제 화면과 완료 플로우를 시뮬레이션한다.

흐름:

1. 전문가 모드 선택
2. 가격 표시
3. 결제하기 버튼
4. 자체 결제 시뮬레이션 화면
5. 결제 완료 화면
6. "현재는 베타 테스트로 실제 결제는 발생하지 않았습니다" 안내
7. 상담 신청, 대기자 등록, 쿠폰 발급 중 하나로 연결

중요 원칙:

- 카드번호, 계좌번호, 주민등록번호 등 실제 결제 민감정보는 입력받지 않는다.
- 사용자가 실제 과금이 발생했다고 오해하지 않도록 완료 화면에서 명확히 안내한다.
- 구매 의사는 결제하기 클릭, 결제 시뮬레이션 진입, 완료 화면 도달, 연락처 제출 이벤트로 측정한다.
- 실제 결제 도입 전까지는 전문가 문서 전체를 즉시 제공하기보다 샘플 미리보기와 상담 신청으로 전환한다.
- 가격은 실제 판매를 가정한 금액으로 표시하되, 베타 단계에서는 실제 청구하지 않는다.

측정 이벤트:

- `expert_price_viewed`: 전문가 모드 가격 확인
- `fake_checkout_started`: 결제하기 클릭
- `fake_checkout_completed`: 결제 시뮬레이션 완료
- `beta_notice_viewed`: 실제 결제 없음 안내 확인
- `waitlist_submitted`: 대기자 등록
- `consultation_requested`: 상담 신청
- `coupon_requested`: 출시 알림/쿠폰 신청

### 7.6 디자인 방향

AI 기획서 챗봇은 기존 포트폴리오 사이트의 무드에서 벗어나지 않게 설계한다. 현재 사이트는 어두운 배경, 얇은 보더, 절제된 surface 컬러, 보라색 accent, 작은 모노스페이스 라벨, 부드러운 hover transition이 핵심이므로 챗봇도 같은 디자인 언어를 사용한다.

핵심 원칙:

- 기존 색상 토큰을 우선 사용한다.
- `--color-bg`, `--color-surface`, `--color-surface-2`, `--color-border`, `--color-muted`, `--color-text`, `--color-accent` 흐름을 유지한다.
- 과한 그라디언트, 네온, 큰 그림자, 장식성 강한 일러스트는 사용하지 않는다.
- CTA는 눈에 띄어야 하지만 포트폴리오 전체보다 튀는 광고 배너처럼 보이면 안 된다.
- 레이아웃은 기존 `max-w-5xl`, `px-4 sm:px-6 lg:px-8`, `sm:px-8` 감각과 맞춘다.
- 모바일에서는 하단 조작 영역을 가리지 않도록 safe-area inset을 고려한다.

### 7.7 플로팅 CTA 디자인

AI 기획서 진입 CTA는 오른쪽 하단에 고정된 플로팅 버튼으로 둔다. 버튼은 원형에 가까운 말풍선 형태로 만들고, "챗봇"이라는 느낌이 즉시 전달되게 한다.

위치:

- 데스크톱: 화면 오른쪽 하단, 기존 레이아웃 여백과 맞춰 `right: max(24px, calc((100vw - 64rem) / 2 + 24px))` 수준의 여백을 사용한다.
- 모바일: `right: 16px`, `bottom: calc(16px + env(safe-area-inset-bottom))` 기준으로 둔다.
- z-index는 헤더보다 높지만 모달보다 낮게 둔다. 예: 헤더 `z-40`, 플로팅 CTA `z-50`, 모달 `z-60`.

형태:

- 기본 크기: 데스크톱 64px, 모바일 56px
- 모양: 원형 버튼에 작은 말풍선 꼬리 또는 말풍선 실루엣
- 배경: `var(--color-surface-2)` 기반, hover 시 `var(--color-accent)`가 은은하게 드러나는 스타일
- 보더: `1px solid var(--color-border)`
- 아이콘: 채팅/메시지 계열 아이콘 사용
- 라벨: 기본은 아이콘 중심, hover 또는 focus 시 짧은 텍스트 툴팁 표시
- 그림자: 어두운 배경에서만 분리될 정도의 부드러운 shadow 사용

CTA 문구 예시:

- "AI 기획서"
- "PRD 만들기"
- "의뢰서 작성"

툴팁 문구 예시:

```text
아이디어만 있어도 기획서를 만들 수 있어요
```

상태:

- 기본: 차분한 surface 버튼
- hover: accent border와 약한 accent glow
- focus: 접근성을 위한 명확한 focus ring
- active: 살짝 눌리는 scale
- unread/attention: 작은 accent dot 또는 짧은 pulse 1회만 사용

주의:

- CTA를 긴 배너 형태로 만들지 않는다.
- 과한 bounce 애니메이션을 반복하지 않는다.
- 원형 버튼 안에 긴 텍스트를 넣지 않는다.
- 오른쪽 하단에 위치하되 본문 카드나 연락처 버튼을 가리지 않게 한다.

### 7.8 챗봇 패널 디자인

CTA 클릭 시 챗봇 패널은 오른쪽 하단에서 열리는 floating panel로 시작한다. 데스크톱에서는 작은 사이드 패널, 모바일에서는 하단 시트 또는 거의 전체 화면 패널로 전환한다.

데스크톱 패널:

- 위치: 오른쪽 하단 CTA 위쪽
- 너비: 380px~440px
- 최대 높이: `min(720px, calc(100vh - 96px))`
- 배경: `var(--color-surface)`
- 보더: `1px solid var(--color-border)`
- radius: 기존 카드보다 약간 큰 16px~20px
- 헤더: 작은 타이틀, 상태 문구, 닫기 버튼
- 본문: 메시지 리스트
- 하단: 입력창, 전송 버튼, 선택지 버튼 영역

모바일 패널:

- 위치: 하단 고정
- 너비: 100%
- 높이: `calc(100dvh - 24px)` 이하
- 상단 모서리 radius: 20px
- 하단 safe-area inset 반영
- 입력창이 키보드에 가리지 않도록 처리

메시지 스타일:

- AI 메시지: `var(--color-surface-2)` 배경, muted text 보조
- 사용자 메시지: accent를 과하게 채우지 않고 border/accent text 중심
- 추천 기능 칩: 작은 pill 버튼, 필수/추천/선택/주의를 색상보다 라벨과 보더 차이로 구분
- 문서 미리보기: 챗 패널 안에서는 요약만 보여주고, 전체 문서는 별도 탭/확장 영역에서 보여준다.

입력 영역:

- 한 줄 입력을 기본으로 하되 긴 답변은 자동 높이 확장
- placeholder는 부담을 낮추는 문장 사용
- 전송 버튼은 아이콘 버튼으로 구성
- 선택지는 버튼형으로 제공하되 텍스트가 넘치면 줄바꿈한다.

### 7.9 디자인 수용 기준

구현 후 다음 기준을 만족해야 한다.

- 기존 포트폴리오의 다크 모던 무드와 색상 체계를 유지한다.
- 플로팅 CTA가 오른쪽 하단에 고정되어 있고, 주요 콘텐츠를 가리지 않는다.
- CTA는 눈에 띄지만 촌스럽거나 광고 배너처럼 보이지 않는다.
- 챗봇 패널은 데스크톱과 모바일에서 모두 읽기 쉽고 입력하기 쉽다.
- 버튼, 칩, 입력창의 텍스트가 넘치거나 겹치지 않는다.
- keyboard focus와 닫기 버튼이 명확하다.
- reduce motion 설정에서는 반복 애니메이션을 끈다.

## 8. AI 에이전트 동작 구조

모든 대화 판단은 OpenAI API를 중심으로 처리한다. 프론트엔드는 대화 상태, 선택 UI, 문서 미리보기, 복사/다운로드 같은 사용자 경험을 담당하고, 질문 생성과 답변 해석은 서버 API를 거쳐 OpenAI API에 요청한다.

### 8.1 상태 모델

대화 상태는 다음 단위로 관리한다.

- `projectType`: 사이트 유형
- `businessSummary`: 사업/서비스 설명
- `targetUsers`: 대상 사용자
- `coreFeatures`: 핵심 기능
- `pages`: 페이지 목록
- `adminNeeds`: 관리자 기능
- `integrations`: 외부 연동
- `designPreference`: 디자인 선호
- `budget`: 예산
- `timeline`: 일정
- `unknowns`: 미정 항목
- `priority`: 우선순위
- `featureCandidates`: 추천 기능 후보
- `selectedFeatures`: 사용자가 선택한 기능
- `excludedFeatures`: 제외된 기능
- `riskAreas`: 기술적 리스크 영역
- `expertMode`: 전문가 모드 활성 여부
- `pricingIntent`: 가격 확인 및 결제 의사 상태
- `fakeCheckoutStatus`: 결제 시뮬레이션 진행 상태
- `generatedDocuments`: 생성 문서

### 8.2 에이전트 단계

1. 의도 파악
2. 프로젝트 유형 분류
3. 사이트 유형별 보편 기능 추천
4. 기능 선택 및 우선순위 분류
5. 필수 질문 생성
6. 답변 누적 및 구조화
7. 누락 정보 확인
8. 기술적 리스크 감지
9. 문서 생성
10. 문서 검토 질문
11. 전문가 모드 제안
12. 최종 출력

각 단계는 고정 if/else 규칙만으로 처리하지 않는다. 서버는 현재 대화 상태를 OpenAI API에 전달하고, API 응답을 구조화된 JSON 형태로 받아 다음 액션을 결정한다.

### 8.3 프롬프트 정책

AI는 다음 원칙을 따른다.

- 비개발자에게 전문 용어를 남발하지 않는다.
- 모호한 답변은 개발자 관점의 요구사항으로 번역한다.
- 모르는 항목은 합리적인 기본값을 제안한다.
- 사이트 유형별로 보편 기능을 먼저 제안하고, 사용자가 선택하게 한다.
- 기능을 추가로 유도할 때는 비용과 MVP 우선순위를 함께 설명한다.
- 예산과 일정은 확정 견적처럼 말하지 않고 범위와 가정으로 표현한다.
- 개인정보, 결제, 의료, 법률 등 민감 영역은 확인 질문과 주의 문구를 추가한다.

### 8.4 OpenAI API 응답 구조

OpenAI API는 자유 텍스트만 반환하지 않고, 프론트엔드가 안정적으로 렌더링할 수 있는 구조화된 응답을 반환하도록 설계한다.

응답 필드 예시:

- `assistantMessage`: 사용자에게 보여줄 자연어 답변
- `nextQuestion`: 다음에 물어볼 질문
- `suggestedFeatures`: 추천 기능 목록
- `featurePriority`: 필수/추천/선택/주의 분류
- `collectedRequirements`: 지금까지 정리된 요구사항
- `missingFields`: 아직 부족한 정보
- `riskAreas`: 기술적 리스크
- `documentDraft`: 생성 중인 문서 초안
- `expertModeRecommendation`: 전문가 모드 추천 여부와 이유
- `uiHints`: 버튼, 체크박스, 선택지 등 UI 렌더링 힌트

이 구조는 예시이며, 실제 구현 시 프론트엔드 상태 관리에 맞춰 조정한다.

### 8.5 전문가 모드 판단 기준

- 결제 승인/취소/환불
- 포인트/적립금
- 입찰/경매
- 채팅/실시간 알림
- 권한이 여러 개인 관리자 시스템
- 대량 엑셀 업로드
- 외부 API 연동

전문가 모드가 필요한 이유를 비개발자에게는 쉬운 말로 설명한다.

예시이며, 실제 설명은 OpenAI API가 프로젝트 맥락에 맞춰 생성한다.

## 10. 데이터 및 보안 고려사항

- AI API 키는 클라이언트에 노출하지 않는다.
- 사용자가 입력한 개인정보는 문서 생성 목적 외에 사용하지 않는다는 안내를 둔다.
- 민감 정보 입력을 최소화한다.
- 생성 문서는 확정 계약서가 아니라 상담용 초안임을 명시한다.
- 문의 전송 시 사용자의 동의를 받는다.
- 전문가 모드 산출물은 최종 기술 보증서가 아니라 개발 착수 전 검토용 설계 초안임을 명시한다.
- MVP의 결제 시뮬레이션에서는 실제 결제 정보를 입력받지 않는다.
- 결제 완료 화면에서는 실제 과금이 발생하지 않았음을 명확히 안내한다.
- 실제 결제 기능을 붙일 경우 환불 정책, 이용 약관, 개인정보 처리방침 안내가 필요하다.

## 16. 최종 PRD 점검

### 16.1 현재 PRD에서 확정된 것

- OpenAI API 기반 챗봇형 PRD/상세 기획서 생성
- 문서 내 질문과 기능 목록은 모두 예시이며 실제 질문/답변은 OpenAI API가 동적 생성
- 정적 React 사이트 기반 UI
- OpenAI API 호출은 클라이언트가 아니라 서버리스 API에서 처리
- 무료 모드와 전문가 모드 분리
- 전문가 모드는 초기에는 실결제가 아니라 결제 의사 검증 플로우로 운영
- PG사 테스트모드가 아닌 자체 결제 시뮬레이션 사용
- 완료 화면에서 실제 결제가 발생하지 않았음을 안내

### 16.2 구현 전 추가로 결정하면 좋은 것

- 전문가 모드 가격
- 결제 시뮬레이션 화면에서 받을 최소 정보
- 상담 신청, 대기자 등록, 쿠폰 발급 중 MVP의 1차 전환 목표
- 생성 문서의 기본 톤: 친절한 상담형 / 개발자 전달형 / 사업계획서형
- OpenAI API 호출당 최대 대화 턴 수
- 하루 무료 생성 횟수 제한
- 문의 데이터 저장 위치

### 16.3 MVP 권장 범위

처음 출시에서는 다음 범위로 제한한다.

- 무료 PRD/상세 기획서 생성
- 전문가 모드 샘플 미리보기
- 가격 표시
- 결제 시뮬레이션
- 실제 결제 없음 안내
- 상담 신청 또는 대기자 등록

실제 결제, 로그인, 문서 저장, 관리자 대시보드는 결제 의사 검증 이후로 미룬다.

### 16.4 리스크

- OpenAI API 비용이 예상보다 빠르게 증가할 수 있다.
- 결제 시뮬레이션이 사용자를 속이는 흐름으로 보이면 신뢰를 잃을 수 있다.
- 전문가 모드의 가치가 문서 미리보기에서 충분히 전달되지 않으면 전환율이 낮을 수 있다.
- 개인정보 수집 시 동의 문구와 보관 정책이 필요하다.

### 16.5 최종 판단

현재 PRD는 MVP 개발에 들어갈 수 있는 수준이다. 다만 첫 구현에서는 기능을 넓히기보다 "무료 문서 생성 완료율"과 "전문가 모드 결제 의사"를 검증하는 데 집중한다.
